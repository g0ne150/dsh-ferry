# 会话流转的传输范围分析

目标只有一个：**换一个 DSH 实例，能把同一件工作接着干下去。**
围绕这个目标，“该传什么”就有了判据——传的是“重建工作现场所需的输入”，而不是“本机的一切”。

判断一个文件是否应该传输，依次问四个问题：

1. **没有它，目标实例还能继续吗？** 源码、文档、lockfile、未提交改动：不能，必须传。
2. **它能否在目标机用确定性方式重建？** `node_modules`、`dist`、`.venv`、`__pycache__`：能，不传，省时间省流量，也避免把 A 机的二进制带到 B 机。
3. **它是否只对这台机器/这个用户有意义？** 绝对路径、socket、终端、后台任务、编辑器状态、本地日志：是，不传。
4. **它是不是秘密？** 令牌、私钥、`.env`：不传。B 机有自己的凭据体系，把 A 的凭据搬过去既是泄密，也常常直接失效。

## 1. 会话本身

会话日志是 DSH 的唯一事实来源，因此**整条日志原样复制**：用户消息、助手消息、工具调用与结果、推理、标题、goal、todo、压缩记录、模型切换等。接收方用同一套事件序列恢复上下文，不需要“摘要”或“重放提示词”。

只改两个字段：

| 字段 | 处理 |
| --- | --- |
| `header.id` | 默认保持不变；目标已有同 id 且内容不同，或用户选择“新会话 ID”时改为新 uuid |
| `header.cwd` | 改为目标实例上的绝对路径（默认同路径，也可显式指定） |

其余头部（创建时间、父会话、agent preset、委派深度）保留，用于溯源；父会话不在目标实例时给出警告。

**不迁移的会话状态**：会话日志之外的运行时状态没有可移植表示，见第 4 节。

## 2. 附件

会话里的图片（截图、图表）和文件附件按内容寻址存储。传输时读取原始字节，在目标实例重新落盘：

- 图片：读取目标实例的规范化对象字节，写入后若附件 id 变化，会同步重写会话日志里的附件引用；
- 文件：逐字节保存，内容哈希不变时 id 保持不变；
- 单次传输有总字节预算（默认 128 MiB），超出部分不传，并在结果里报告“附件不完整”警告；会话日志里的引用会悬空，聊天里对应图片无法显示，但文本与工具历史不受影响。

## 3. 工作区文件

### 3.1 传输

| 类别 | 说明 |
| --- | --- |
| 源码与脚本 | 所有未被忽略规则排除的普通文件 |
| 文档与配置 | `README`、`AGENTS.md`、配置模板、CI 配置等 |
| 锁文件 | `pnpm-lock.yaml`、`package-lock.json`、`poetry.lock`、`Cargo.lock` 等，保证目标机装出同样的依赖 |
| 未提交改动 | 文件级内容会带过去（`.git` 也传时，`git status` 能继续看到改动） |
| 空目录 | 保留目录结构（有些工具依赖目录存在） |
| 相对符号链接 | 目标仍落在工作区内的链接会重建；指向外部或绝对的链接跳过 |
| `.git` | 见 3.3，默认在大小上限内包含 |

文件权限的可执行位、修改时间会尽量保留（Windows 上忽略 chmod）。

### 3.2 默认不传输及理由

| 类别 | 典型路径 | 理由 | 可配置覆盖 |
| --- | --- | --- | --- |
| 依赖树 | `node_modules/`、`.venv/`、`.pnpm-store/`、`Pods/`、`.gradle/`、`.m2/` | 可在目标机用锁文件重建；体积大、含本机编译产物 | `workspace.include` 可点名，但不建议 |
| 构建产物 | `dist/`、`build/`、`out/`、`.next/`、`target/` | 由源码生成，跨平台常不可用 | 同上 |
| 缓存 | `.cache/`、`.turbo/`、`.pytest_cache/`、`__pycache__/`、`coverage/`、`*.log` | 纯本机加速/诊断数据 | 同上 |
| 编辑器/IDE | `.idea/`、`.vscode/` | 本机窗口布局、扩展设置 | 同上 |
| OS 垃圾 | `.DS_Store`、`Thumbs.db`、`desktop.ini` | 与工作无关 | 同上 |
| 凭据 | `.env`、`.env.local`、`.npmrc`、`*.pem`、`*.key`、`id_rsa*`、`.ssh/`、`.aws/`、`.kube/config`、`credentials.json` | 泄密风险；目标机有自己的凭据 | 仅 `includeSecrets: true` 或 `include` 显式点名 |
| 模板文件 | `.env.example`、`.env.sample`、`.env.template`、`.env.dist` | 本就是给人看的模板，不含秘密 | 默认包含 |
| 超大文件 | 单文件 > `maxFileBytes`（默认 64 MiB） | 传输成本与误传风险 | 调大上限或 `include` 点名（仍受上限约束） |
| 外部符号链接 | 指向工作区之外或绝对路径 | 目标机上不存在同样目标，可能指向敏感位置 | `symlinks: inside` / `skip` |
| 特殊文件 | socket、FIFO、设备文件 | 无法跨机重建，也没有工作含义 | 不可覆盖 |
| 传输暂存 | `.dsh-ferry-*` | 本插件自己的暂存/备份 | 不可覆盖 |

`.gitignore`（以及工作区根目录的 `.dsh-ferry-ignore`）默认参与判断，可用 `respectGitignore: false` 关闭；用户还可用 `workspace.exclude` / `workspace.include` 追加规则（`include` 不能绕开凭据与大小限制）。

### 3.3 `.git` 策略

Git 历史对“继续工作”很有价值：分支、stash、未推送提交、未提交改动都靠它。但 `.git` 也可能非常大，且 `.git/config` 可能内嵌远端凭据。

默认 `git: auto`：

- `.git` 是目录且总大小 ≤ `maxGitBytes`（默认 64 MiB）→ 随包传输（跳过 `*.lock`、`worktrees/`、`lfs/tmp/`）；
- 超过上限 → 跳过并报告，目标机应自行 `git clone` / `git fetch`；
- `.git` 是文件（worktree 指针）→ 跳过并报告；
- 目标目录已有 `.git` → 保留目标自己的历史，不覆盖，并在结果中提示；
- 传输 `.git` 且其 config 形如 `scheme://user@host` → 给出“可能含凭据”的警告。

`git: include` 仍受硬上限约束；`git: skip` 完全不传。也可以在工作区里放 `.dsh-ferry-ignore` 精确控制个别文件。

### 3.4 大小、合并与备份

- 工作区总字节超过 `maxWorkspaceBytes`（默认 1 GiB）→ 拒绝传输，并报告实际大小，让用户调大上限或缩小范围。
- 目标目录非空时必须显式 `merge`；合并时逐文件比对内容哈希：
  - 相同 → 跳过（不触碰 mtime）；
  - 不同 → 先备份旧文件到 `<dataDir>/backups/<时间戳>-<会话>/`，再原子替换；
- 落盘分两阶段：先写目标目录内的 `.dsh-ferry-partial-<随机>` 暂存目录并逐文件校验 SHA-256，全部通过后才移动到最终位置；失败则清理暂存并可回滚已写入的文件。
- 目标目录的选择顺序：显式指定 → 本机已存在同路径则复用 → 否则放到 `workspace.incomingRoot` 下（`<源目录名>-<源工作区指纹>`，指纹由「发送实例 + 源路径」算出）。缺失的源路径不会被凭空创建。
- 指纹按工作区算，不按会话：同一源目录的多个会话共用一个子目录，否则每推一个会话就会多出一份工作区副本。
- 导入路径逐段检查父目录不是符号链接，避免借已存在的软链写到 `importRoots` 之外。

## 4. 不随会话迁移的运行时状态

这些对象没有可移植的持久表示，或者强绑定本机进程，迁移它们等于伪造状态：

| 对象 | 为什么不能迁移 | 目标机怎么办 |
| --- | --- | --- |
| 终端 PTY / shell 会话 | 进程与文件描述符属于源机内核 | 重新开终端 |
| 后台 job（bash、子进程） | 同上，输出缓冲也在源进程内 | 重跑命令；需要长期运行的改由目标机启动 |
| 日程 / 定时提醒 | 由本机 schedule 服务与存储持有，且触发要唤醒本机会话 | 在目标机重新创建 |
| 子会话（subagent / team） | 有独立会话日志与父子关系；父会话迁移后关系会悬空 | 默认只迁移当前会话；需要时逐个拉取 |
| 审批 / 待回答提问 | 属于当前进程的交互状态 | 目标机重新发起 |
| LSP / 浏览器 / 计算机使用会话 | 绑定本机进程与外部程序 | 重新建立 |
| 被 spill 的大工具输出 | 只在本机 spill 存储中 | 需要时重跑工具 |
| 模型凭据与账号 | 属于本机 profile | 目标机用自己的配置 |

插件的解释是：**会话日志负责“知道什么”，工作区负责“改到哪”，其余交回给目标机的真实环境。** 任何试图把进程状态序列化过去的方案，都只能得到一份无法继续推进的假状态。

## 5. 失败、幂等与冲突

| 场景 | 行为 |
| --- | --- |
| 同 id、同内容重复推送 | 追加更新时只同步工作区（0 条事件）；新建会话时复制一份 |
| 对方是旧副本（本机已续写） | 追加更新：补上缺失事件并合并工作区，覆盖前备份 |
| 两边都续写过（分叉） | 拒绝追加，提示新建会话；对方副本保持原样 |
| 对方副本更长 | 拒绝追加，提示新建会话或改从对方拉取 |
| 目标目录非空且未勾选合并 | 拒绝，不做任何写入 |
| 单文件/总大小超限 | 在传输前拒绝，或跳过并报告（取决于是硬上限还是单文件规则） |
| 校验和失败 | 终止导入，清理暂存，回滚已应用文件 |
| 附件读取失败 | 跳过该附件并警告，会话其余部分照常 |
| 工作区挂载失败 | 会话已创建但未挂到工作区，结果里警告 |
| 会话格式版本不一致 | 传输前拒绝，提示两端升级到同一 DSH 版本 |

## 6. 已知边界

- 历史事件里的绝对路径不会改写：目标路径变化后，旧工具调用记录仍指向源机路径；模型需要重新确认当前目录。
- 只迁移一个会话及其工作区；不会自动把整个工作区里其它会话的上下文带过去。
- 没有文件级增量：每次传输都带完整工作区清单，重复内容靠逐文件哈希跳过写入，但网络传输不跳过；事件层面则只追加缺失部分。
- 追加只追加事件，不改会话头部：对方副本的 cwd、标题、模型预设保持对方导入时的样子。
- `.git` 会连同远端配置一起复制（可能含凭据），只给警告不脱敏；不希望如此就用 `git: skip`。
